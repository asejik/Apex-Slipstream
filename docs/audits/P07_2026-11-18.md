## 4. Detail

### R10-05 (MEDIUM): the CI browser tests are unreliable

Championship journey times on GitHub's `windows-latest` with WARP (`gh run view --log`):

| Run | Branch | Championship journey |
|---|---|---|
| 44332765926 | #77 | 2.5 min (Quick Race failed at 6.2 min, then passed on retry) |
| 44340050725 | #78 | 2.9 min |
| 44342710158 | main | 6.8 min |
| 44344758880 | #79 | **10.0 min, failed; retry 9.5 min, failed** (`Test timeout`) |
| 44345650139 | main (same code) | 3.6 min, passed |

- **Impact:** a red CI on a correct change (#79 was merged with a red check), or a pass that says nothing. A whole run takes 14–28 min.
- **Cause:** the software renderer's speed varies about 4× between runs. The journeys wait in real time (the start lights, driving to 30 km/h), so a slow machine runs out of time.
- **Fix options** (needs your choice):
  1. Make race time independent of frame rate in tests: step the game in fixed steps from the test instead of waiting on frames.
  2. Run only the build journeys (offline, security policy) on CI, and the race journeys locally on the GPU.
  3. Raise the limits to 10 minutes and accept 30-minute runs.
- **Verify:** 5 CI runs in a row, all green, under 15 minutes.

### P07-R02 (MEDIUM): saves can be lost
- **The code:** career, season, settings, key bindings and driver live in `localStorage`; ghosts live in IndexedDB. There is no `navigator.storage.persist()` call (grep: 0) and no export or import.
- **Impact:**
  - Clearing site data, private browsing, or the browser making room deletes the save.
  - Safari deletes a website's script-written storage after 7 days without use, unless the site was added to the Home Screen.
  - If you play on an iPhone in Safari and pause for a week, the career may be gone.
- **Fix:**
  - (S) Call `navigator.storage.persist()` once after the first race.
  - (S) A "Copy save" / "Paste save" pair in Settings, as one JSON string of the six keys.
  - (S) Tell iPhone players to add the game to the Home Screen.
- **Verify:** Settings → Copy save, clear site data, Paste save; the career is back.

### P07-R01 (MEDIUM): first load on a slow phone

Simulated in Chromium, as Lighthouse's mobile setting: 150 ms latency, 1.6 Mbps, 4× slower CPU, 740×360 at 2×, live site, no service worker:
```
run1 {"lcp":5588,"cls":0.009,"fcp":976,"hubReadyMs":6116,"tapToPaintMs":366}
run2 {"lcp":5880,"cls":0.008,"fcp":1012,"hubReadyMs":6284,"tapToPaintMs":365}
```

- **What happens:** the page starts drawing at about 1 s. The hub (the largest content) appears only after the 210 KB game code, the fonts and the 243 KB car model have arrived and three.js has built the scene behind it.
- **The tap time** is the Records tab, measured to the next painted frame, while the 3D scene keeps drawing behind the hub.
- **Fix ideas:**
  - Show the hub's DOM before building the 3D scene.
  - Load the car model after the hub is up.
  - Compress the model (P12-R01).
  - Draw the background scene less often while a menu is open.
- **Repeat visits** load from the offline cache (#77), so this mostly hits the first visit.
- **Verify:** run the same measurement again; the target is under 2.5 s.
